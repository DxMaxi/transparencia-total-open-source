# Auditoria técnica aprofundada — 2026-08-15

## Âmbito

Esta auditoria revê o estado técnico do projeto Transparência Total / Fator Cívico com foco em:

- frontend público;
- backend FastAPI;
- PostgreSQL e ciclo de vida da API;
- autenticação Supabase;
- CI/CD;
- Vercel e Render;
- PWA/service worker;
- dependências;
- tratamento de indisponibilidade;
- testes automáticos;
- higiene do repositório;
- gates necessários para fechar a V5.

Issue de acompanhamento: **#76**.

Plano V5: **#58**.

## Resultado executivo

No checkpoint auditado não foi confirmada nenhuma falha **P0** do tipo fuga ativa de credenciais, autenticação completamente contornável, perda de dados em curso ou comprometimento conhecido do site.

Foram, no entanto, identificados vários achados **P1**, **P2** e **P3** que devem ser tratados ou explicitamente encerrados antes do release final V5.

A existência de suites verdes não deve ser interpretada como prova de ausência de bugs. Esta auditoria encontrou falhas de integração e resiliência fora da cobertura atual dos testes.

## Estado de remediação — 2026-08-20

Este documento preserva o diagnóstico histórico. O código posterior acrescentou:

- Playwright no CI contra o artefacto Next local e no smoke após deployment de produção;
- rate limit explícito para escritas públicas, sem persistir a origem em claro;
- ativação, alteração e revogação de alertas por consentimento;
- difusão reconstruída apenas a partir de `CitizenAlert` publicado e fonte atestada;
- exclusão dos relatórios Playwright do Git;
- exclusão do manifesto e service worker do proxy de autenticação;
- alvo focável para o skip-link;
- allowlist explícita para a runtime cache;
- documentação do build Next canónico e do adaptador vinext.

O rate limit incluído é local a cada processo. Uma implantação horizontal continua a exigir um
limitador partilhado. CSP sem `unsafe-inline`, evidência final do ambiente, staging, recuperação e
gates jurídicos permanecem condições separadas; esta nota não os declara concluídos.

## Escala de prioridade

- **P0** — incidente crítico/comprometimento ativo. Bloqueio imediato.
- **P1** — bug ou risco material que bloqueia o release V5 enquanto confirmado e aberto.
- **P2** — deve ser corrigido ou formalmente mitigado antes do candidato final.
- **P3** — hardening, higiene, acessibilidade ou dívida técnica que deve ficar rastreada.
- **VERIFICAR** — hipótese relevante ainda sem evidência suficiente para classificar como defeito confirmado.

# P1 — bloqueadores de release

## P1.1 — Dependências Python divergentes no Render

### Evidência

- `backend/app/core/staff_auth.py` importa `jwt`.
- `backend/pyproject.toml` declara `PyJWT[crypto]==2.13.0`.
- `backend/requirements.txt` não declara PyJWT.
- `render.yaml` usa `pip install -r requirements.txt`.

### Risco

Uma instalação limpa de produção pode depender de uma dependência transitiva/acidental para fornecer `jwt`, ou falhar quando essa dependência deixar de existir.

### Correção esperada

Definir uma fonte canónica de dependências Python ou garantir sincronização automática entre ficheiros, seguida de instalação limpa e testes.

### Teste exigido

Instalação do backend num ambiente limpo usando exatamente o comando de build de produção e import/teste de `staff_auth`.

---

## P1.2 — Falha parcial de perfil pode tornar-se 404 falso

### Evidência

`loadPublicPolitician()` consulta o estado global e o endpoint do perfil separadamente. A página `app/politicos/[slug]/page.tsx` chama `notFound()` quando `loaded.data` é nulo e o estado global não é `UNAVAILABLE`.

### Cenário problemático

1. `/api/v1/public/data-status` responde `LIVE`.
2. `/api/v1/public/politicians/<slug>` sofre timeout/503/erro transitório.
3. `data` fica nulo mas `status.mode` continua `LIVE`.
4. a página pode responder como perfil inexistente.

### Risco

- mensagem factual errada ao utilizador;
- 404 temporário para um recurso que existe;
- possível impacto SEO/caching;
- repetição da classe de erro já corrigida na homepage: indisponibilidade técnica convertida em significado factual.

### Correção esperada

Transportar o estado do pedido do perfil separadamente do estado global e distinguir explicitamente:

- 404 real;
- 422/erro de pedido;
- 503/timeout/indisponibilidade;
- sucesso.

### Teste exigido

Teste de regressão onde `data-status=LIVE` e o endpoint do perfil falha, provando que a resposta não é 404.

---

## P1.3 — Public smoke não prova o deployment correspondente ao commit

### Evidência

`.github/workflows/public-smoke.yml` corre em `push` para `main` e também por schedule. O smoke consulta o domínio público, mas o workflow não prova que a versão servida pela Vercel corresponde ao SHA do commit que disparou a execução.

### Risco

O smoke pode ficar verde enquanto ainda testa a versão anterior durante a janela de deployment.

### Correção esperada

Associar o smoke pós-release a evidência verificável do deployment do SHA, ou introduzir um mecanismo equivalente de prova de versão antes de aceitar o gate.

### Teste exigido

Pipeline deve falhar se o site público ainda não corresponder ao commit esperado dentro do período definido.

---

## P1.4 — Startup da API depende diretamente do PostgreSQL

### Evidência

No `lifespan` da aplicação é executado `await repository.connect()` antes de a aplicação começar a servir pedidos. `PostgresRepository.connect()` cria o pool asyncpg imediatamente.

### Risco

Durante restart/deploy, uma BD temporariamente indisponível pode impedir a aplicação de arrancar e, por consequência, impedir até uma rota de liveness puramente processual de responder.

### Correção esperada

Separar semanticamente:

- processo vivo;
- dependência BD pronta;
- API funcional para leitura pública.

A solução não deve esconder uma BD indisponível; deve permitir diagnóstico correto.

### Teste exigido

Arranque da API com PostgreSQL indisponível deve produzir comportamento deliberado e testado para liveness/readiness.

# P2 — corrigir antes do candidato final

## P2.1 — Playwright existe mas não corre no CI

A cobertura E2E browser foi adicionada ao repositório, mas o workflow CI atual executa contratos Node, lint, build e testes backend sem instalar browser Playwright nem executar `tests/e2e`.

**Ação:** adicionar etapa CI adequada e evitar duplicação excessiva com smoke público.

## P2.2 — Paridade Python CI/produção

No checkpoint auditado:

- CI: Python 3.12;
- Render: Python 3.13.5;
- projeto: `requires-python >=3.12`.

Isto pode ser aceitável como matriz de suporte, mas deve ser uma decisão explícita e testada, não uma divergência acidental.

**Remediação implementada no código:** a revisão exata passa a ser definida em
`.python-version` (`3.13.15`). Todos os workflows com `actions/setup-python` leem esse ficheiro;
Render e Docker declaram a mesma revisão; `requires-python`, Ruff e mypy ficam limitados à série
3.13. O verificador `backend/scripts/check_python_runtime_policy.py` impede nova divergência e o CI
confirma também o intérprete efetivamente instalado. O fecho desta ocorrência continua dependente
de CI verde e da confirmação read-only de que o deployment Render do commit integrado usa a mesma
revisão; o patch, por si só, não prova o estado de produção.

## P2.3 — Duas fontes de dependências Python

`backend/requirements.txt` e `backend/pyproject.toml` contêm listas independentes. A ausência de PyJWT numa delas demonstra deriva real.

**Ação:** definir fonte única ou verificação automática de equivalência.

## P2.4 — `/public/data-status` deve degradar de forma controlada

As restantes rotas públicas relevantes convertem `RuntimeError` de indisponibilidade em HTTP 503. O endpoint de estado deve ter comportamento igualmente explícito, evitando 500 genérico quando a BD não está disponível.

## P2.5 — Promessómetro pode apresentar fallback como LIVE

`loadPublicPromises()` devolve `initialGovernmentCommitments` quando o endpoint de promessas não entrega dados, mas no checkpoint auditado mantém `showingFallback:false`.

Se o `data-status` global continuar `LIVE`, o `DataModeBanner` pode apresentar a experiência como dados publicados normais apesar de o módulo ter usado fallback.

Os compromissos de fallback são conteúdo oficial/editorial conhecido, não dados fictícios; o problema é **estado incorreto do módulo**.

## P2.6 — Falhas frontend→API têm pouca observabilidade

`apiFetch()` converte exceções num simples `{ ok:false }`.

Isto reduz capacidade de distinguir de forma segura:

- timeout;
- DNS/ligação;
- resposta não-2xx;
- JSON inválido;
- abort;
- falha de infraestrutura.

A observabilidade adicionada não deve expor payloads, tokens ou informação sensível.

## P2.7 — Timeout global de 4 segundos

O cliente de dados públicos usa `AbortSignal.timeout(4_000)`.

A falsa apresentação de zeros já foi corrigida, mas um cold-start ou latência transitória pode continuar a produzir indisponibilidade visual.

**Ação:** medir antes de mudar. Avaliar timeout, retry bounded, stale-data e caching sem esconder erros reais nem servir dados desatualizados como atuais.

## P2.8 — Rate limiting/anti-abuso

A revisão final de #54 já exige verificação de rate limiting. As rotas públicas de escrita e recursos suscetíveis a abuso devem ter política explícita antes do release.

## P2.9 — Alertas push devem ser revogáveis

A UI atual permite subscrever e entra em estado `enabled`, mas a experiência completa de preferências/revogação ainda pertence à #55.

O release final deve garantir que o utilizador consegue remover a subscrição no browser e backend.

# P3 — hardening, acessibilidade e higiene

## P3.1 — CSP com `unsafe-inline`

A configuração de segurança é ampla, mas `script-src` e `style-src` ainda permitem `unsafe-inline` onde necessário para a stack atual.

**Ação:** investigar nonces/hashes/compatibilidade Next.js sem remover diretivas de forma cega.

## P3.2 — Artefactos Playwright fora do `.gitignore`

Adicionar pelo menos:

```text
/test-results/
/playwright-report/
/blob-report/
```

ou equivalentes corretos para a configuração usada.

## P3.3 — Dois caminhos de build

`npm run build` usa o pipeline vinext enquanto CI relevante usa `npm run build:next`.

**Ação:** documentar qual é o build canónico de Vercel/release e em que contexto o vinext continua necessário.

## P3.4 — `.vinext/` versionado

Foi observada a presença de `.vinext/fonts` no repositório e `.gitignore` não exclui `.vinext/`.

Não remover automaticamente. Confirmar primeiro se é um artefacto intencional da plataforma/build.

## P3.5 — `manifest.json` atravessa o proxy Supabase

O matcher exclui `manifest.webmanifest`, mas a aplicação publica `/manifest.json`.

Se o manifest não precisa de sessão, deve ser excluído explicitamente para reduzir trabalho e acoplamento.

## P3.6 — Skip-link e gestão de foco

O skip-link aponta para `#conteudo`, atualmente um `div`.

Avaliar foco real por teclado e tecnologias de apoio; alterar apenas com teste de acessibilidade correspondente.

## P3.7 — Política de runtime-cache do service worker

O service worker já protege áreas privadas, pedidos com Authorization e respostas `private/no-store`.

Como hardening futuro, considerar allowlist explícita de recursos públicos em vez de depender apenas da exclusão de áreas privadas, sobretudo à medida que novas rotas forem adicionadas.

## P3.8 — Ambiente local suportado

O projeto exige Node 24.x. Testes locais usados como evidência de release devem correr no runtime suportado.

# VERIFICAR antes do release

## V1 — Ficheiros de dados grandes no repositório

Existem artefactos JSON de auditoria sob `data/`. O conteúdo de alguns ficheiros grandes não foi integralmente inspecionado durante a auditoria remota.

Antes da release final executar pesquisa local específica por:

- NIF;
- emails;
- telefones;
- moradas;
- tokens/chaves;
- identificadores pessoais não destinados a publicação;
- conteúdo privado de revisão.

Não assumir que o facto de um ficheiro provir de fonte oficial torna todo o seu conteúdo apropriado para Git público.

## V2 — Contacto institucional em produção

Confirmar que o canal público/institucional configurado no deployment é o esperado sem imprimir secrets ou variáveis privadas em logs/issues.

## V3 — Pesquisa final de segredos

Repetir no candidato final:

- working tree;
- histórico Git;
- artefactos CI;
- ficheiros gerados;
- documentação pública.

### Verificação de 24-08-2026

A primeira repetição integral foi concluída e documentada em
[V5.19 — auditoria de privacidade e segredos do candidato](V5_RELEASE_PRIVACY_AUDIT.md):

- os quatro JSON versionados em `data/` não contêm emails preenchidos, campos NIF/NIPC, contactos
  ou marcadores de segredo;
- Gitleaks 8.30.0, com artefacto validado por SHA-256, analisou 297 commits;
- os cinco alertas foram revistos como UUID sintético de teste ou placeholder explícito;
- a pesquisa específica encontrou zero identidades `age`, chaves privadas, secret keys Supabase,
  chaves OpenAI ou JWT completos;
- um email pessoal removido do estado atual continua presente em diffs históricos.

O último ponto mantém a visibilidade pública bloqueada e exige uma decisão separada antes de
qualquer reescrita de história ou force-push. A pesquisa deve ser repetida no commit candidato e
depois de uma eventual reescrita.

# Aspetos positivos confirmados no checkpoint

A auditoria não é uma avaliação exclusivamente negativa. No checkpoint existiam proteções importantes:

- distinção entre recolha/staging/revisão/publicação;
- regras fail-closed em fluxos editoriais relevantes;
- PWA com exclusão de áreas privadas e respostas `private/no-store`;
- headers HTTP de segurança extensos;
- suite frontend conhecida a 64/64 após a correção de indisponibilidade;
- smoke público automatizado;
- `npm audit --omit=dev` previamente sem vulnerabilidades reportadas;
- pesquisa anterior de segredos sem credenciais reais conhecidas;
- regra pública de não substituir indisponibilidade por dados fictícios.

Estas proteções devem ser preservadas ao corrigir os achados.
